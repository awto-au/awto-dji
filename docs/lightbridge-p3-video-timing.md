Date 2026-10-30. Tags: V shown in code/capture, I inferred, U unknown. Paths under awto-dji are read-only sources.
Scripts here: sweep.py (bitstream), mbmap.py + mb_full.log (ffmpeg MB types), interleave.py, duml_mix.py, moduli2.py, cascade.py. Tool: scripts/annexb_slice_stats.py (generic, committed 28e271197).

## A1. Pilot app (DJI GO / dji.pilot midware, decompiled dji/midware/media/)
- Decoder = stock android MediaCodec "video/avc" to a Surface, no KEY_LOW_LATENCY, no output-corrupt/concealment flag (DJIDecodeServer.java:~850-900). `flags`=2 int in MediaFormat; KEY_OPERATING_RATE only on Exynos.
- START (V, DJIDecodeServer.java:741-766): while "iframe not set" (f11419g false) the server drops frames until a frame is flagged key OR has frameNum==1 (e(): aVar.f11427h==1). Then, if the frame is not a key frame, it loads a bundled raw resource (`a(w,h)` -> DJIVideoDecoder.getIframeRawId) and queues it as the first input ("queuein a default iframe"), clears the queue, sets iframe-set, then feeds real frames. So GO does NOT wait for an IDR on P3: it injects a canned IDR.
- Resource for P3 Professional (litchiX): not in the switch -> default `iframe_1280x720_ins` (DJIVideoDecoder.java:1334-1337); P3 Adv/Std (litchiS/C) -> `iframe_1280x720_3s`. File res/raw/iframe_1280x720_ins.h264: 607 B = SPS + PPS + 8 IDR slices; its PPS bytes `68 ee 3c b0` and SPS profile/level `64 00 32` are identical to the live stream's (SPS first 24 bytes equal, one VUI bit differs). 3s variant has level 0x28, different PPS.
- ProductType.isGDR defaults true (ProductType.java:54-60); false only for Mavic Pro / Mavic (KumquatX/S) = DJI's own name for this stream class is GDR (gradual decoder refresh). libdjivideo has `trans_gdr_duration`; RecorderManager.BufferMode.GDR_ONLINE/GDR_OFFLINE.
- LOSS (V): input queue LinkedBlockingQueue(15) (DJIDecodeServer.java:136-138); on overflow, non-WM240 products drop the OLDEST queued frame (poll + onFrameDropped, :248-255); WM240/WM245 (needFetchIframe) instead clear the queue and raise "error status" (DataOldSpecialControl) to force an I-frame. frame-number skips are only logged/statted (e.java FrameNum_Skip); SEI-embedded CRC/length check (e.java a(aVar,i)) and index continuity check run only for needFetchIframe products. Decoder stall: dequeueInputBuffer(10 ms) fails 20 times in a row -> m(): clear queue, codec.flush(), iframe-set=false -> next eligible frame re-injects the canned IDR (f.java n()). resetKeyFrame (msg 10) does the same without flush (source switch, ServiceManager.m()).
- Output: every decoded buffer is rendered (releaseOutputBuffer(i,true)); nothing is blanked on loss, so the last picture stays; decoder-side concealment is whatever the phone codec does (U).
- Not found in the dump: any caller of DataCameraRequestForIFrame (partial dex dump; U whether GO sends it on P3).
- U: how libdjivideo computes isKeyFrame / frameNum for the raw P3 stream (needs arm64 disassembly). Candidate: SPS/PPS-bearing AU counts as key (I).

## A2. Our implementation
- VideoShim.kt:162-191 (commit 92b0023, on main): same bootstrap, read from the installed `dji.go.v4` package, resource `iframe_1280x720_ins`; queued first. Issue #26 comment "no special GDR-tolerance code" and STREAM_SPEC section 7 are stale/incomplete: the bootstrap IS the GDR tolerance. Hard dependency on GO being installed (else no bootstrap, U what MediaCodec does).
- Differences: pending queue 300 (VideoShim.kt:200) vs GO 15 (worst case ~12 s of latency vs ~0.6 s); no flush/reset on stall; onError sets configured=false and clears queues but nothing restarts the codec (:131-147), GO resets and re-bootstraps; no frame-skip/drop-oldest policy beyond the 300 cap; no 10 ms dequeue timeout concept (async callbacks); timestamps = System.nanoTime()/1000 at submit (:232); Dart side groups NALs into AUs (h264_access_units.dart); manual + on-connect RequestIFrame (aoa_transport.dart:147, :212) which per #26 never yields an IDR.

## A3. Intra refresh in live-camera.h264 (V; sweep.py + scripts/annexb_slice_stats.py --mbmap, ffmpeg -debug mb_type)
- 1613 AUs, 26 SPS+PPS AUs, 0 IDR, 0 SEI, 0 recovery-point SEI, all slices P. SPS spacing: 60 AUs x12, rest 54-59 (capture loss), two gaps 90/117.
- Each SPS AU starts a SWEEP: 9 slices of 400 MB (5 MB rows = 80 px) instead of the normal 8 slices of 480 MB (6 rows, last 240). AU k (k=0..8) carries slice at first_mb 400k as intra (I MBs, 17-31 KB), rows above it P-coded (3.5-7 KB), rows below it skip-only slices (17-45 B); 10th AU (k=9) repeats rows 0-4 intra (21 KB). 185 AUs have the 9x400 layout; 180 sit at offsets 0..9 after an SPS AU, 5 are outliers (SPS lost in capture).
- ffmpeg MB map confirms: frame with SPS shows rows 0-4 all-intra, next frames rows 4-9, 9-14 ... 39-44; 13 clean 9-frame sweeps, start spacing 60 frames x18 in the MB-map pass. Outside sweeps ~64 intra MBs/frame (1.8%), scattered, no rolling row/column, no column runs.
- Period 60 AUs = 2.4 s at 25 fps; sweep 9-10 AUs = 0.36-0.40 s. A decoder that joins mid-cycle shows the canned picture in unrefreshed areas until the next sweep (<= 2.4 s + 0.4 s). AU size ~19 KB steady (no keyframe spike); sweep AUs 14-42 KB.
- Therefore: the stream is not refresh-less: it is a band-wipe GDR with SPS/PPS as the cycle marker (no SEI recovery point). Dan's keyframe point is right (no IDR, loss tolerated, last frame stays up); the correction is that recovery is guaranteed within one 2.4 s cycle by design, and that the pilot app bootstraps with a canned IDR rather than waiting.

## B2. FPGA image counters (m2001, from the pluribus netlist lift)
- 267 counters; 16 have a recoverable modulus (self-clear = pure compare): 29, 30, 10,000,000 (24 b), 62,500 x2 (16 b), 384, 768, 2304, 256, 96, 100,000, 192, 65, 24, 23, 48. The other 251 clear/load through LUT cones (modulus not recovered: absence of a frame counter is not proven).
- Clock domains (image_clocks.json, docs/cycloneiv-clean-pll-clocks.md): 6 roots; 235 of 267 counters on PLL_8 c0 (clkbuf 0_46_30, 20,472 FFs), 21 on PLL_8 c3 (clkbuf 0_46_31, 10,530 FFs): 192, 24, 48 counters are on c3, all others of the 16 on c0. c0 : c3 = 2 : 1 (post-scale 2, c0 4/4, c3 8/8). Fin unknown: c0 in [96.1, 208.3] MHz, c3 in [48.1, 104.2] MHz.
- Enable cones (<= 2 FF hops, structural not proven carry): 384 enable includes the 2304 counter (ratio 6); 2304 enable includes the 192 and 24 counters ; 24 enable includes the 192 counter; 192 enable from an unclassified counter; 96, 768, 23 enabled from unclassified counters. So a hierarchy exists: 192 (c3) -> 24 (c3) -> 2304 (c0) -> 384 (c0) (I).
- Ratios: 2304/768 = 3, 768/96 = 8, 2304/96 = 24, 2304/192 = 12, 768/192 = 4, 192/24 = 8, 384/192 = 2, 96/48 = 2.
- No counter of 97 (video symbols/burst), 136/137 (symbols/14 ms frame) or a 14 ms period (1.3-2.9 M clocks at c0 range). 10,000,000 and 100,000 and 62,500 look like timers (e.g. 100 ms / 1 ms if c0 = 100 MHz, in range; I, Fin unproven). No TDD frame/slot/symbol counter hierarchy is visible in the recovered moduli; this does not rule it out (FSM / M9K table / unrecovered cones).

## B3. IEEE 802.16 comparison (standard values from memory, not re-checked against the text here; fit statements are inference)
- WirelessMAN-OFDM (256-FFT): 192 data + 8 pilots + 56 null; TDD frame (2.5-20 ms list) = DL subframe (preamble, FCH/DLFP, DL-MAP, UL-MAP, DCD/UCD, bursts) + TTG + UL subframe + RTG; burst profiles (DIUC/UIUC) = modulation (BPSK/QPSK/16/64QAM) x FEC rate, each burst a whole number of OFDM symbols. OFDMA 1024-FFT: PUSC 720 data + 120 pilots; AMC bins = 9 carriers (8 data + 1 pilot) -> 96 bins = 864 used = 768 data + 96 pilots.
- Measured Lightbridge numerology (docs/lightbridge-phy-measured.md, Matrice 100 proxy): 1024-FFT, 11.2 MS/s, 10.9375 kHz, CP 1/8, 102.857 us symbol (1152 samples), 864 used = 768 + 96, one pilot per 9 carriers = WiMAX 10 MHz profile / AMC carrier set (V for numerology, I for the mapping). Frame 14.000 ms (156,800 samples = 136.11 symbols, not an integer and not in the 802.16 frame list) with a ~9.98 ms (97 symbol) video burst and a 2.2 ms narrowband hopping second link in the gap (V on M100, not captured on P3).
- Counter fit (I): 768 = data carriers, 96 = pilots, 192 = 768/4, 24 = 96/4, 384 = 768/2, 48 = 96/2; 2304 = 3 x 768 (e.g. 768 carriers x 4 b x 3/4 or x 6 b x 1/2 payload bits per symbol) = 2 x 1152 samples. 192 also equals the 256-FFT data-carrier count, but the measured link is 1024-FFT so a 256-FFT meaning is unlikely. Bit rate sanity: 97 sym x 768 b = 74.5 kb per 14 ms = 5.3 Mb/s (QPSK-class payload) vs ~3.9-4.2 Mb/s video + DUML (I).

## B4. Timing model (conclusion)
- Strict "1 video frame, 1 DUML frame" alternation: rejected at the FX3/phone stream (DUML 10 Hz vs 25 AU/s, 0.4 DUML chunk per AU, not AU-aligned, DUML = 5-7 frames per chunk).
- Fits best: DUML sent on a ~100 ms timer-driven batch at the ground FX3 (UART path, separate from the video DMA); video is a continuous byte stream with PKTEND at each AUD. Air-interface: video + DUML + control share an OFDM burst of ~97 symbols every 14 ms (V for burst/frame, I for the sharing); fixed slots per radio frame (71.4 Hz) are plausible for the radio layer (I) but then DUML is re-batched at 10 Hz by the ground side; nothing observed shows a per-frame (25 Hz) DUML slot.
- Unknown: how DUML bytes are carried in the OFDM payload (in-burst vs the 2.2 ms second link, per-frame slot size, FEC/CRC, header); P3 radio frame length (only M100 measured); isKeyFrame/frameNum rule in libdjivideo; whether GO sends RequestIFrame on P3; Fin of PLL_8 (c0/c3 absolute rate); whether the ground FPGA carries DUML to the UART at all or m1400 gets it over SPI; timing below 1 s resolution (captures stamp seconds only); the sweep generator on the air side (DM365 TI codec setting).
