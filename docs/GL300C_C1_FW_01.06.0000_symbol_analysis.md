# DJI GL300C remote controller: C1 v01.06.0000 symbols and module identities

Updated: 2026-10-25

## Summary

The DJI remote-controller firmware package `C1_FW_V01.06.0000.bin` has publicly available reverse-engineered symbol files for **both** `m1400` and `m1401`. The distinction matters when analysing a **GL300C** controller. The available documentation identifies `m1400` with the older LPC1765-related branch (GL300A/GL300B) and `m1401` with the LPC1549-related GL300C branch. These labels should still be verified against the target's hardware and DUML routing before treating them as proof of its processor identity.

**Key correction:** Do **not** conclude from the older `m1400` string alone that the GL300C's firmware has been updated independently. Check the corresponding `m1401` firmware and its build identity first.

## Observed identities

| Source | Reported identity / date | Interpretation |
|---|---|---|
| `C1_FW_V01.06.0000` `m1400` | `WM610 A7_1765 20160321/01` | Older LPC1765-related module; not a like-for-like GL300C comparison. |
| `C1_FW_V01.06.0000` `m1401` | 2016-03-24 build date reported in community analysis | More relevant GL300C candidate; verify exact embedded version string from the extracted image. |
| Live GL300C DUML GetVersion response | `WM320_A7_LPC1 20170828/00` | Device-reported identity dated 2017-08-28. The specific responder/module needs confirmation from the DUML source/device IDs. |

The 2017 live response is later than the 2016 firmware samples. **This is evidence of a mismatch, not yet proof that the same submodule was independently upgraded**: firmware branches, device ID routing and version-string formats may differ.

## Interesting `m1401` MAP entries

These identifiers were directly observed in the `C1_FW_V01.06.0000_m1401.map` public file:

| MAP entry | Indicative relevance |
|---|---|
| `App_TaskAdcKey_Worker` | Key/stick input processing |
| `App_TaskLedBell_Worker` | LEDs/buzzer |
| `App_TaskRadio_Worker` | Radio-related task |
| `App_TaskUnpack_Worker` | Packet unpacking |
| `packet_hw_receive` | Packet reception |
| `packet_prepare_response` | Packet response construction |
| `packet_send` | Packet output |
| `get_board_version` | Board-identification logic |
| `ofdm_init_instruction` | OFDM/Lightbridge setup |
| `init_fpga_config` | FPGA configuration setup |
| `cmd_exec_set00_cmd01` and numerous other `cmd_exec_setXX_cmdYY` | DUML-like command handlers for investigation |

The names are **community reverse-engineering annotations** and should be checked against actual control flow, not assumed to be official source symbols.

## Recommended next steps for `awto-dji`

1. Parse the C1 firmware container and inventory every module and submodule. Record module identifiers, lengths, hashes, architecture and build strings.
2. Extract `m1401` from the verified `C1_FW_V01.06.0000.bin` and match it to the public symbol set. Preserve the original binary and checksum.
3. Load the extracted ARM image into Ghidra with the correct image base, architecture and memory layout. Convert the MAP/IDC annotations to Ghidra importable labels as required. Avoid blindly applying file offsets as runtime addresses.
4. Locate the embedded `m1401` version string and compare its full value, not just its build date, with the live GL300C response.
5. Recheck the captured live DUML GetVersion **receiver/source identifiers**, command set and command ID. Confirm the precise responding MCU before declaring the binary to be the same component.
6. Identify and document the bootloader/update code, flash map, USB interfaces and module-specific routing without writing or flashing the hardware.
7. Compare the `m1400` and `m1401` command handlers only after accounting for their different processor families and memory maps.

## Open questions

- Does the 2017 `WM320_A7_LPC1` response originate from the MCU represented by `m1401`, or a different MCU/subsystem?
- What is the **complete** embedded identity string in the 2016 `m1401` image?
- Is there a later public GL300C firmware container with a matching 2017 build?
- Which component exposes the Micro-USB service connection, if any, and which physical USB endpoint is active on the GL300C?
- Are `m1401` symbols stable across different firmware revisions, or should function matching be based on signatures/control flow?

## Project caution

The C1 package version `01.06.0000` identifies a **container release**, not necessarily the build date or running version of each internal firmware module. A matching container hash establishes the integrity/identity of the downloaded package, **not** equivalence to firmware currently flashed in the GL300C. Do not attempt an on-device downgrade based solely on these file names.
